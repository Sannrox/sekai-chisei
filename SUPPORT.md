# Support

Use the channel that matches the request so maintainers can respond without
moving sensitive or actionable reports later.

## Questions and usage help

Start a [GitHub Discussion](https://github.com/Sannrox/sekai-chisei/discussions)
for setup questions, integration guidance, and ideas that are not yet a
concrete change request. Include:

- the command or integration you are using;
- the relevant platform and Rust version;
- the expected and observed behavior; and
- sanitized logs or receipts when they help explain the problem.

Remove credentials, tokens, provider payloads, private prompts, database files,
and identifying production data before posting.

## Bugs and feature requests

Search [existing Issues](https://github.com/Sannrox/sekai-chisei/issues) first.
If the problem or request is new, open the matching Bug, Feature, Refactoring,
or Research form. Keep one focused outcome per Issue and include a minimal
reproduction for bugs when possible.

Use a Design Discussion before implementation when a proposal changes a public
contract, crosses the Sekai/Chisei boundary, changes the namespace or trust
model, or is difficult to reverse. The
[contributor guide](CONTRIBUTING.md#before-you-start) explains the project
workflow.

## Security vulnerabilities

Do not report exploitable vulnerabilities in Discussions or public Issues.
Follow the private disclosure process in [SECURITY.md](SECURITY.md).

## Support expectations

`sekai-chisei` is a maintainer-led open-source project. Support is best effort;
there is no guaranteed response time or service-level agreement.
Maintainers may convert a support request into an Issue when it identifies a
reproducible defect or a scoped change.
